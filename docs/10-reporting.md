# 10 — Reporting and remediation rendering

**Owner: Track E. Phase 1 for the first PDF, refined through Phase 5.**

Deliverable 4 in the problem statement, quoted almost verbatim: *one PDF per device: device
identity including serial and hardware, pass/fail with severity, and device-specific
step-by-step remediation CLI.*

The test that matters is not whether the PDF renders. It is **cold-read usability**: hand a
generated report to someone unfamiliar with the project, and if they cannot act on the
remediation without narration, the report has failed its actual purpose.

## Per-device report structure

| Section | Contents | Why it is there |
|---------|----------|-----------------|
| 1. Device identity | Vendor, model, OS version, **serial**, hostname, source files, audit timestamp | Explicitly required. Serial usually comes from `show version`, not the running config. |
| 2. Posture summary | Score, findings by severity, findings by state, framework selected | The one page a manager reads. |
| 3. Coverage statement | *parsed 12,847 of 13,102 lines (98.1%)*, per-tier attribution | Invariant 4. The number commercial tools hide. |
| 4. Findings | Per finding: id, title, severity, state, cited file and line, raw line, rationale | Invariant 2. Every finding points at a line number. |
| 5. Remediation | Ordered CLI in the device own vendor syntax, grouped and sequenced safely | The deliverable that makes the report actionable. |
| 6. Verification evidence | For DEMONSTRATED findings: probe, response, packet capture digest | Crucible output, the claim nobody else can make. |
| Appendix A | Full rule set version and framework mapping table | Reproducibility. |
| Appendix B | Attack paths this device participates in | Fleet context on a per-device page. |
| Appendix C | Uninterpreted lines, verbatim | Invariant 3, made checkable rather than merely stated. |
| Footer | Report id, ledger sequence, Merkle root prefix, verification hash | Tamper evidence, on every page. |

## Finding states in the report

Three states, printed as three visually distinct things, never collapsed into pass and fail.

| State | Printed as | Means |
|-------|-----------|-------|
| DEMONSTRATED | Red, with a proof block | Reproduced live against a twin. Probe, response and capture attached. |
| ASSERTED | Amber | The rule matched parsed facts. Not runtime-testable, or the twin could not model it. |
| UNKNOWN | Grey, listed in Appendix C | Could not parse the relevant configuration. Not a pass. |

A reader who only remembers one thing should remember that grey is not green.

## Remediation rendering

Remediation comes from the versioned rule files, rendered per target. It is never generated by a
model and never retrieved from standards text — that is the one place hallucination would be
unforgivable, because an administrator pastes it into a production firewall.

Three properties the renderer must guarantee:

1. **Self-lockout safety.** The sequence never disables the transport the administrator is
   connected over before the replacement transport is up. Enable SSH, verify, then disable Telnet
   — never the reverse.
2. **Ordering across findings.** Individually safe fixes can be jointly unsafe. The renderer
   orders the full set, not each fix in isolation.
3. **Per-step rollback.** Every step carries its inverse, so a half-applied change can be backed
   out from a console session.

Where Crucible has validated the sequence against a twin, the report says so explicitly. Where it
has not, it says that too.

## What-if projection

Before and after: the compliance score the device would have if the printed remediation were
applied, computed by re-evaluating the rule set against the IR as the remediation would leave it.
It is a projection, labelled as one, and it is what turns *312 findings* into a decision.

## Fleet report

One additional document per audit job: fleet posture, cross-device correlations, the attack-path
graph, and the ranked remediation list ordered by paths severed rather than by CIS severity. The
sentence it exists to support is *these three devices are individually compliant; together they
expose the core; here is the one fix that severs forty-seven paths.*

## Licensing constraint in generated output

CIS Benchmark text is never reproduced in a report. Control identifiers are cited deterministically
from rule metadata, rationale prose is our own, and full control text is quoted only from STIG and
NIST sources. A report generator that pastes benchmark text is a licensing problem, not a feature.
